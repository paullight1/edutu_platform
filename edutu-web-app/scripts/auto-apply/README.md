# Auto Apply browser provider

Run the local Chromium check with `node scripts/auto-apply/pilot-smoke.mjs` from the web package. Add `--multi-page` to exercise a two-page provider with an intermediate POST. It creates a temporary form and synthetic learner, fills the form in Chrome, attaches a PDF generated from the reviewed CV text, submits the reviewed draft, checks the returned receipt and verifies that repeating the submission creates no second form post.

Mobile groups the review by provider page when a mapping has multiple steps. Start the local API pilot with `AUTO_APPLY_TEST_MULTI_PAGE=1` and run `node scripts/auto-apply/check-simulator-pilot.mjs --multi-page` to check the review grouping, first-page edits, and both posts after approval.

Use `AUTO_APPLY_TEST_MULTI_PAGE_INTERRUPTION=1` and `--multi-page-interruption` to return HTTP 401 after the first POST. The test checks that Edutu preserves the unconfirmed state, allows a receipt check, and blocks replay of the first page.

Run `node scripts/auto-apply/browser-provider.mjs` with Chrome installed and the following environment variables.

| Variable | Value |
| --- | --- |
| `AUTO_APPLY_FORMS_FILE` | Path to the approved opportunity mappings, keyed by opportunity UUID |
| `AUTO_APPLY_PROVIDER_TOKEN` | Shared secret matching the learner API worker configuration |
| `AUTO_APPLY_RECEIPTS_DIR` | Persistent private directory for receipt references and idempotency reservations |
| `AUTO_APPLY_PROVIDER_PORT` | Local listen port, default 7718 |
| `AUTO_APPLY_PROVIDER_BIND_HOST` | Listen address, default `127.0.0.1` |
| `AUTO_APPLY_BUNDLED_CHROMIUM` | Set to `true` to use the Chromium shell installed with Playwright |
| `CHROME_PATH` | Optional Chrome executable path |

Point the worker’s HTTPS prepare and submit URLs to the adapter’s `/prepare` and `/submit` paths through a TLS reverse proxy. Use the same origin for both. Configure the optional worker receipt URL to the adapter’s `/receipt` base path so Edutu can recover a stored receipt without replaying the form. The adapter listens on loopback. Supply the matching opportunity IDs to the worker through `AUTO_APPLY_PILOT_OPPORTUNITIES`. For the bundled Chromium adapter, set `AUTO_APPLY_PROVIDER_CAPABILITIES_URL` to its same-origin HTTPS `/capabilities` endpoint and set `AUTO_APPLY_PROVIDER_VERIFY_URL` to its same-origin HTTPS `/verify` endpoint. The API requires the read-only form verification before every new attempt. It sends only the opportunity ID and the adapter credential, and the verification opens mapped pages without filling controls or submitting them.

For each opportunity, configure `url`, `submitSelector`, `receiptSelector`, and `fields`. Each field has a unique `label` and `selector`, a `source` drawn from `background`, `statement`, `name`, `email`, `answer`, or `cv_pdf`, and an optional `question` shown when the source has no value. For a missing `statement` field, the worker can draft text using Edutu’s existing statement-of-purpose AI route. It sends the mapped question, the catalog summary, saved application background, and selected academic and work details from the chosen CV. If the AI cannot supply a usable draft, Edutu asks the learner to enter the statement. The learner reviews the draft before approval. For a dropdown, set `source: "answer"` and `control: "select"`. Edutu shows the currently enabled option labels and sends the provider’s corresponding value after review. The smoke test contains a complete mapping. For multiple pages, use a top-level `receiptSelector` and a `steps` array containing each page’s `url`, `fields`, and `submitSelector`. Each page must be directly viewable for review. Edutu opens each page without clicking submit during preparation, then follows the real step transitions after approval. Configure only approved forms with supported text inputs, single-choice dropdowns, or PDF attachment fields, same-origin POST submission, and an identifiable receipt. An optional `handoffSelector` identifies a sign-in or other provider-controlled step on a mapped page. Edutu can open the official listing link for the learner. Session transfer, other attachment types, and authenticated form preparation need provider-specific adapters.

Use `school`, `degree`, `major`, or `graduationYear` as the source for application profile education. School, degree, and major are saved as text. Graduation year uses four digits. For a select or radio group, the saved value must match a single enabled label. Edutu asks the learner to choose when the saved value is missing, ambiguous, or spelled differently on the form. The learner can correct each value during review.

Use `phone` for a mapped contact number. Edutu uses the learner’s application profile first, then the selected CV. If neither supplies a usable number, Edutu asks the learner or leaves the value blank when the mapping and live field both allow it.

The preparation response includes the destination host and a revision derived from the approved mapping and the live form structure, including each page’s POST destination, field labels and input constraints. Preparation reads the live form and keeps learner values in Edutu. After approval, the adapter preflights every page against that revision before filling any control or attaching a CV. It validates the populated form again before each POST. Forms with unmapped required fields, preselected answers, or checked declarations require a mapping update or provider handoff. Drafts prepared under an older revision format require a fresh review. A receipt reservation survives process restarts. An existing reservation without a receipt requires manual verification with the provider before any resubmission. Use a single adapter instance or shared durable reservation storage when deploying replicas.

The worker records when a submission may have been handed to the adapter. If an expired worker lease proves dispatch had yet to start, another worker resumes the approved attempt. Once dispatch is possible, Edutu checks for a receipt. Claims from older worker versions also use receipt checks because they lack the dispatch marker.

Set `catalogUrl` on a mapping to bind it to the current HTTPS application link in the catalog. This link can point to a landing page whose mapped application form is hosted elsewhere. Edutu compares the normalized link, including its path and query parameters, before starting, preparing, and submitting the attempt. A changed link stops Auto Apply until the mapping is checked and updated. The required verification endpoint must return the same binding before a new attempt can use the learner’s allowance. The capabilities endpoint can provide a faster readiness signal while live verification remains authoritative.

For a read-only form check on new starts, set `AUTO_APPLY_PROVIDER_VERIFY_URL` to the same-origin HTTPS `/verify` endpoint. This variable is required for new starts. If it is missing or unavailable, Edutu fails closed and leaves the tracked draft available without using the monthly allowance. A successful fresh verification must include a non-empty `catalogFingerprint` matching the current catalog application URL. A mapped sign-in or security step can still open a learner handoff. Existing attempts remain accessible while the provider is enabled.

To verify staging from the web package, run `node scripts/auto-apply/verify-mapping.mjs <opportunity-uuid> <catalog-application-url>`. Supply the provider prepare URL and token through the environment. Set `AUTO_APPLY_CHECK_API_URL` to the exact HTTPS API base used by the staging mobile build and `AUTO_APPLY_CHECK_LEARNER_TOKEN` to a short-lived session token for a staging learner with no existing attempt for that opportunity. The script checks the mapped provider form, the learner's allowance endpoint, and availability for a new attempt. It uses GET requests and exits unsuccessfully on a route, authentication, mapping, or availability failure.

Start a fresh pilot with `AUTO_APPLY_TEST_FORM_PREFLIGHT=1` and run `node scripts/auto-apply/check-simulator-pilot.mjs --form-preflight`. The test checks that a new unmapped required field costs zero attempts, a provider handoff can still start, and resuming and submitting it uses the original attempt.

To verify catalog-link changes, start an isolated pilot with `AUTO_APPLY_TEST_CATALOG_LINK=1`. Run `node scripts/auto-apply/check-simulator-pilot.mjs --catalog-link` from the API package. It checks that a stale link uses no allowance before start, stops an already approved attempt before a portal write, and reuses the attempt after the link is restored and reviewed again.

New Auto Apply attempts require a configured HTTPS submission endpoint on the same adapter origin. Start the pilot with `AUTO_APPLY_TEST_SUBMIT_CONFIG=1` and run the checker with `--submit-config` to verify that a missing or invalid endpoint blocks starts without using an attempt. An already saved review remains available and can be approved once the endpoint is restored.

Edutu includes a text field’s native `maxlength` in review when it is below the 16,000-character draft limit. Learners can shorten a saved or AI-written answer in review. The API and adapter check the browser’s UTF-16 length before submission.

When the mapped statement is missing, the adapter reads the form before requesting a draft. Edutu gives the model the statement field’s character limit and asks the learner for their own statement if the model’s draft exceeds that limit.

To verify the manual statement limit, start a fresh pilot with `AUTO_APPLY_TEST_SOP_RESULT=insufficient` and run `node scripts/auto-apply/check-simulator-pilot.mjs --manual-statement`. It checks that a statement exceeding the ITU field’s limit is rejected while the question stays open for revision.

To verify separate essay drafts on the same form, set `AUTO_APPLY_TEST_STATEMENT_PROMPTS=1` and run `node scripts/auto-apply/check-simulator-pilot.mjs --statement-prompts`. Map each essay with its own `question`. Edutu prepares the questions separately and shows both responses in the review. The fixture uses simulated model responses and checks that the two distinct statements reach the intended portal fields.

Edutu checks native field formats in a blank browser page before filling the provider form. Use an optional `formatHint` for a field with a custom pattern. Apply `20261127055000_auto_apply_answer_format.sql` before rolling out this behavior. Apply `20261127062000_auto_apply_correction_alert.sql` for dedicated format, review correction, and provider handoff alerts. Set `AUTO_APPLY_TEST_NATIVE_VALIDATION=1` and run `node scripts/auto-apply/check-simulator-pilot.mjs --native-validation` to verify corrections during preparation and after a review edit.

Map a native provider `<select multiple>` with `control: "multi-select"` and `source: "answer"`. Edutu asks the learner to choose the labels, including an explicit skip for optional fields, and shows the choices in the draft. Apply `20261127060000_auto_apply_multiple_choices.sql` before enabling these mappings. Start the pilot with `AUTO_APPLY_TEST_MULTIPLE_CHOICES=1` and run `node scripts/auto-apply/check-simulator-pilot.mjs --multiple-choices` to verify the choices and exact submitted values.

When a required mapped phone field has no usable saved value, learners can opt to save an international number to their Auto Apply profile. The current form keeps the learner’s original answer, and later drafts use the normalized number. Apply `20261127064000_auto_apply_save_phone.sql` before rolling out the prompt. Start the pilot with `AUTO_APPLY_TEST_REMEMBER_PHONE=1` and run `node scripts/auto-apply/check-simulator-pilot.mjs --remember-phone` to verify cross-opportunity reuse and preservation of an existing number.

For an optional text field, set `optional: true` in the mapping. Edutu shows an empty value in review when the learner has supplied no answer. Learners can add or clear the value before approving. If the live form requires the field, Edutu stops preparation and reports the form change. File uploads and choice controls require an answer when included in a mapping.

Use `statementContext: true` on a mapped free-text question about the learner’s goals or relevant experience when its answer should inform an AI-drafted statement. Put those questions before the statement in the mapping. Edutu supplies at most eight answered questions from the current attempt and uses the latest answer for each. Keep contact details and identity questions outside this context. Mapped questions must have distinct wording across all steps.

The adapter rejects concurrent work before opening a browser context with `503` and `{"code":"provider_busy"}`. The API defers that attempt up to four times with increasing delays. Read-only preparation also backs off after temporary HTTP or connection failures. For an approved submission, the API keeps the same approved version and defers only when the adapter explicitly reports that it was busy before opening the browser. Submit failures with an unknown outcome go through receipt reconciliation.

Auto Apply checks the catalog deadline before creating an attempt, at learner approval, and when the worker claims preparation or submission. Date-only listings stay open through their closing day in UTC. An older attempt and its receipt remain accessible after the opportunity closes.

Chromium checks each redirect against the reviewed origin. A standard same-origin POST-to-GET redirect can open the next step or show the receipt. A redirect that would resend a POST or leave the reviewed origin is blocked. If the portal redirects off-site during preparation, Edutu prompts the learner to open the provider site. If a write may already have occurred, Edutu checks for a receipt before drawing a conclusion.

An optional `handoffPath` on a mapped step can point directly to a stable public section such as `/documents#references`. It must stay on the mapped origin and use no query parameters. Without an explicit path the adapter uses the mapped page when its URL is stable. A mapping bound with `catalogUrl` can expose its mapped step on a different host as long as the catalog link still matches. For older unbound mappings, Edutu exposes steps on the catalog application’s origin. Edutu opens the current catalog link when it cannot share a step.

Set `AUTO_APPLY_TEST_BOUND_HANDOFF=1` and run the simulator checker with `--bound-handoff` to exercise a catalog listing and a TLS-protected form on separate origins. The check changes the catalog link while the attempt is paused and verifies that the old step is replaced with the current listing link.

Set `handoffQuestion` alongside `handoffSelector` to tell the learner what to do when that visible element appears. For example, use `Complete the security check on the provider’s website.` for a verified challenge indicator. A visible mapped challenge takes precedence over the HTTP status. A `429` without that indicator remains a temporary failure and uses preparation backoff.

Handoffs prefer the catalog’s `application_url` and use `apply_url` as a fallback. African Leadership University links use the applicant’s manual flow under [ALU’s admissions policy](https://www.alueducation.com/apply-now/). The local ALU fixture uses a loopback form and remains available for testing the attachment flow.

For a native radio group, use `source: "answer"` and `control: "radio"`. The selector must match all radio inputs with the same name in one form. Edutu presents the enabled labels as choices, lets the learner correct their answer in review, and validates the selected value against the live form after approval. Use provider handoff for attestations, agreements, or consent that must be completed on the provider’s site.

`name` and `email` fields use the learner’s confirmed application contact details, with the selected CV as a fallback. An answer supplied for that application takes precedence. The contact details are kept separate from the background used to draft the statement of purpose. Edutu captures the application profile when the learner starts an attempt. Changes from the Application profile screen are used by new attempts. A learner can edit the review of an in-progress application.

Use `source: "support_pdf"` for up to three original PDFs totaling 10 MiB, in addition to an optional generated CV. Each file has its own mapped question. The learner selects saved documents or uploads them from their device and reviews each selection before submission. Preparation sends only document metadata to the private adapter. Submission verifies the checksum of each original file. Apply the supporting-documents migration and update the API and adapter before enabling mappings with multiple PDF fields. Allow a 16 MiB request body on the private adapter’s submit route.

For a native checkbox, set `source: "answer"`, `control: "checkbox"`, and `checkboxLabel` to the exact provider wording, with repeated whitespace collapsed. The learner chooses explicitly even when the provider prechecks the box. Optional boxes support leaving it unchecked. The review displays the provider wording and the selected response. Linked, indeterminate, ambiguous, and changed labels require handling on the provider site.

Set `AUTO_APPLY_PROVIDER_CV_PREVIEW_URL` to the adapter’s same-origin HTTPS `/preview-cv` endpoint to enable **Open or share CV PDF** on mobile. The preview uses the saved review version and the same PDF renderer as submission. It renders without visiting the provider form.

## Dokploy browser service

For a limited learner pilot, set `AUTO_APPLY_PILOT_LEARNERS` on the API to the comma-separated Clerk user IDs of the opted-in learners. An empty value blocks new starts for everyone. Existing attempts stay accessible and can continue while the provider remains enabled. An unset value allows new attempts for any eligible learner on configured pilot opportunities.

Set the Docker build context to `edutu-web-app/scripts/auto-apply` and use the `Dockerfile` in that directory. Run one replica with an init process and a graceful stop timeout of at least 65 seconds. The image bundles the Chromium headless shell that matches the locked Playwright version. Chromium launches as the `node` user with its sandbox enabled. The runtime needs working unprivileged user namespaces and a seccomp policy that permits Chromium to create them. [Playwright container guidance](https://playwright.dev/docs/docker#crawling-and-scraping)

- Mount the approved mapping file read-only as `/config/forms.json`. Supply `AUTO_APPLY_PROVIDER_TOKEN` as a runtime secret.
- Mount private durable storage at `/var/lib/edutu-auto-apply` with read, write, and directory access for UID 1000. The container requires the mount at startup. Keep that volume through upgrades and rollbacks. Back up receipt reservations with the same access controls as the live volume.
- Route API worker traffic through HTTPS to port 7718. Permit browser egress only to reviewed provider hosts and deny private, loopback, link-local and metadata destinations at the network boundary, including on redirects. Keep the browser service isolated from the datastore and other internal services.
- Verify `/healthz` returns `200` before enabling any opportunity IDs in the API worker. It returns `503` when the browser disconnects or the receipt directory becomes inaccessible. Restart the service to load changed mappings.
- Before enabling a mapped opportunity, use `node verify-mapping.mjs <opportunity-uuid> <current-catalog-application-url>` from this directory with the worker’s prepare URL and adapter token in the environment. It checks that the provider form can be inspected, that its mapping matches the application URL, and that receipt storage is accessible. The check opens mapped pages without filling controls, attaching files, or submitting. A verified mapping still needs a separate receipt and device notification test.
- For rollout, run the fixture checks and confirm receipt lookup still works after restarting the service with its volume attached. To roll back, clear the pilot IDs and keep the original adapter’s prepare origin, receipt URL, token, and mounted receipt volume available. Edutu stops preparing and sending new work while it continues reading receipts for unresolved submissions. Test this path with `AUTO_APPLY_TEST_UNCONFIRMED=1 AUTO_APPLY_TEST_ROLLBACK_RECEIPT=1` and the checker’s `--rollback-receipt` option. Apply `20261127073000_auto_apply_receipt_notification.sql` to link verified submission notifications to the exact receipt screen.

## Dokploy staging worker

Use `.dokploy/auto-apply/compose.staging.yaml` as a Docker Compose service on the staging host. Attach the staging API and this Compose worker to a dedicated internal, attachable overlay network. Give only the worker a separate egress network that permits traffic to the approved provider sandbox and blocks private and link-local destinations, including metadata endpoints. The Compose worker has no published port or Dokploy domain.

Set `AUTO_APPLY_STAGING_API_NETWORK` and `AUTO_APPLY_STAGING_EGRESS_NETWORK` to those network names. Supply `AUTO_APPLY_PROVIDER_TOKEN` to both services through their runtime settings. Mount the approved provider sandbox mapping through `AUTO_APPLY_STAGING_MAPPING_FILE`. Set `AUTO_APPLY_STAGING_CERT_FILE`, `AUTO_APPLY_STAGING_KEY_FILE`, and `AUTO_APPLY_STAGING_CA_FILE` to absolute paths on the Compose host. The certificate must cover `auto-apply-adapter.staging.internal`. The worker runs as UID 1000 and needs read access to these files.

Mount the same CA certificate on the staging API and set its `NODE_EXTRA_CA_CERTS` to the in-container CA path. Configure the staging API's `AUTO_APPLY_PROVIDER_PREPARE_URL`, `AUTO_APPLY_PROVIDER_VERIFY_URL`, `AUTO_APPLY_PROVIDER_CAPABILITIES_URL`, `AUTO_APPLY_PROVIDER_SUBMIT_URL`, `AUTO_APPLY_PROVIDER_RECEIPT_URL`, and `AUTO_APPLY_PROVIDER_CV_PREVIEW_URL` at `https://auto-apply-adapter.staging.internal:7718`, using `/prepare`, `/verify`, `/capabilities`, `/submit`, `/receipt`, and `/preview-cv` respectively. Keep the pilot IDs empty until the worker is healthy from the staging API and the sandbox mapping has been verified. Preserve its receipt volume when redeploying.
